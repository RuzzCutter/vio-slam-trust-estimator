## 0. Зафиксированные решения

| Вопрос | Решение |
|--------|---------|
| Где гонять | Только локальный стенд. Старые RESULT_DIR там. При необходимости докачиваем EuRoC MH, не новые семейства датасетов. |
| Повторы | N **независимых пусков одного и того же bag**, одинаковые конфиг и деградация. Бюджет достаточный; лучше с запасом, часть пусков отпадёт. |
| `start_offset` | **Не менять между пусками.** Это отсечение взлёта, а не рандомизация. MH_04 = 15 с, MH_05 = 5 с (`config/datasets.yaml`). |
| ORB-SLAM3, V1_03, KITTI, TUM-VI, натурка | В этой версии **не запускаем**. |
| Цифры из черновика руководителя (v4/v5) | Формат таблиц (mean±std, p, failure, корреляция) берём. Конкретные значения **не** переносим. |
| Диск | Перед серией освободить место. Битый git-коммит (2026-08-20) был из‑за пустых объектов при ~93 % диска. |

Почему offset не варьируем. Сдвиг старта меняет состав траектории и долю «грязного» взлёта. Тогда разброс ATE смешивает повторяемость фильтра и разный входной отрезок. Независимость пусков даёт ROS/init/тайминг при **том же** отрезке bag — это как раз то, что видно по старому расхождению 0,448 м vs 2,630 м на «одинаковом» adaptive.

## 2. Правила приёмки прогона (заранее, до серии)

Иначе «отбросить выброс» станет подгонкой.

### 2.1. Протокольный срыв (не входит в ATE)

Уже есть в стенде; оставляем и **обязательно** пишем в манифест:

- сбой инициализации OpenVINS;
- разрыв траектории > 0,5 с;
- расхождение: |координата| > 50 м;
- нет пары est/GT для `evo` (нет метрик).

Счётчики: `n_launch`, `n_fail`, `n_success`. В статье failure rate = n_fail / n_launch.

### 2.2. Успешный прогон

Есть TUM-траектория, `evo` посчитал ATE/RPE, нет флагов из §2.1.

### 2.3. Что не отбрасываем по ATE

Высокий ATE при формально успешной траектории (как 2,630 м) — **не** выброс для удаления из основной статистики. Это неустойчивость метода, её нужно видеть в std, медиане и min–max.

Дополнительно можно пометить run как `ate_high` (ATE > Q3 + 1,5 IQR **внутри той же ячейки и того же режима**), но:

- в **основной** таблице остаются все `n_success`;
- trim-таблица — только в приложении / журнале, с явным правилом.

Запас пусков — из‑за срывов init, а не чтобы выкинуть неудобные ATE.

### 2.4. Объём пусков на стенде

| Серия | Ячейки | Пусков на ячейку | Зачем |
|-------|--------|------------------|--------|
| Compare | 10 условий `batch_paper.yaml` × baseline+adaptive | **9** независимых compare (каждый = 1 baseline + 1 adaptive) | ≥5 успешных **пар** на ячейку после срывов |
| Ablation | 4 сценария × {w/o f1..f4} | **7** adaptive на вариант | Full **не** гоняем отдельно: успешные adaptive из compare |
| Карта / корреляция | успешные adaptive MH_04 clean и MH_04 D1 σ=5 (минимум) | по всем успешным этих ячеек | Медиана r по пускам, не один прогон |

Если после 9 пусков успешных пар < 5 — догоняем **только** эту ячейку ещё 3–5 пусками (`--resume`).

Оценка порядка: ~10×9 compare + 4×4×7 ablation ≈ 90 compare-ячеек + 112 ablation-пусков. Compare-ячейка — два полных bag. Это много часов; batch уже умеет `--resume`.

Ячейки плана compare:

| Seq | clean | D1 σ=5 | D1 σ=9 | D3 +40 % | D3 +60 % |
|-----|-------|--------|--------|----------|----------|
| MH_04_difficult | да | да | да (в пилоте не было ATE) | да | да |
| MH_05_difficult | да (в пилоте срыв) | да (срыв) | да (срыв) | да | да |

Трудные по пилоту (MH_05 D1, MH_05 clean, MH_04 D1 σ=9) **не** исключать заранее: failure rate — результат.

## 3. Этап A — доработка ПО (до серии)

Делать в этой ветке. Полные MH — только после smoke.

### A1. Повторы в batch

Файлы: `scripts/run_batch.py`, `config/batch_paper.yaml`, `config/batch_ablation.yaml`.

- В плане: `repeats: 9` (compare) / `repeats: 7` (ablation).
- Каждый повтор — новый `RESULT_DIR` (timestamp в имени). **Не** подмешивать seed в MSCKF.
- В `manifest.jsonl`: `repeat`, `seq`, `degrade`, `mode`/`ablate_variant`, пути, ATE, RPE, c̄, флаги срыва, `n_poses`.
- `start_offset` только из каталога или явного `advanced.start_offset`; для повторов не рандомизировать.
- Сохранить `--resume`.

Идентичность bag: тот же путь к (деградированному) bag, тот же `openvins_config` / `euroc_mav_trust`, те же `trust_tau`, `c_skip`. Деградированные bag из `datasets/euroc/degraded/` не пересобирать между повторами.

### A2. Сводка статистики для статьи

Файлы: `scripts/lib/run_results.py`, `scripts/build_tables.py`.

Для каждой ячейки (seq × condition × режим):

- n_launch, n_fail, n_success;
- median, mean, std (sample, ddof=1) ATE и RPE по успешным;
- min, max;
- mean c̄ по успешным adaptive;
- для compare: парный t-тест по **согласованным** повторам (повтор k: baseline_k vs adaptive_k), только если n_success пар ≥ 5; иначе p не публиковать, в таблице «—».

Выход: `paper_tables/table_repeats.md`, `.csv`, `.tex` — колонки как у руководителя (ATE base/adapt mean±std, ΔATE по **медианам**, p, c̄, Failure = n_fail/n_launch), числа только с новой серии.

ΔATE считать по медианам. В тексте можно дублировать mean.

Гипотеза на чистых: выполняется, если median(ATE_adapt) ≤ 1,05 · median(ATE_base).  
На деградации: median(ATE_adapt) < 0,9 · median(ATE_base).  
t-тест — дополнительный аргумент, не замена порогов (`эксперимент_v2.md`).

### A3. Общий adaptive-full для табл. 1 и 2

- Ablation-план **без** отдельных `full`.
- `build_tables.py --kind ablation` берёт full = успешные adaptive compare той же (seq, degrade).
- В markdown ablation: строка full совпадает с adaptive табл. 1 (те же n и median).

### A4. Поштучная ошибка и корреляция с доверием

Файлы: `scripts/evaluate_trajectory.py`, новый `scripts/correlate_trust_ate.py` (или расширение `build_trust_map.py`).

- При `--eval` сохранять поштучные ошибки после Sim(3): таблица `t, e_ate_m` рядом с `summary.txt`.
- Выровнять с `trust_log.csv` по времени (логика align уже есть в `build_trust_map.py`).
- Считать: Pearson и Spearman c(t) vs e(t); то же для скользящего окна (окно 2 с или 20 отсчётов — зафиксировать в `meta.json`); доля кадров c < c_skip; квантили c: p10, p50, p90.
- По ячейке: медиана r по успешным пускам, размах, доля пусков с p < 0,05.
- Карты C(x,y): для медианы-по-ATE пуска и для худшего успешного — две картинки в статью.

Если |r| окажется мал — в статью идёт факт, не цель «получить −0,72».

### A5. Журнал серии и smoke

После каждого batch — короткий апдейт `журнал_эксперимента.md`: id каталога, n_launch/n_fail, команды resume. Источник истины — `manifest.jsonl`.

Smoke **до** полной серии:

```text
python3 scripts/run_batch.py --plan config/batch_paper.yaml --dry-run
# затем 2 повтора MH_01 --duration 60 (или отдельный smoke-plan)
```

Критерий: два RESULT_DIR, два манифест-ряда, сводка n=2 без падения скрипта.  
Полные MH_04/MH_05 не начинать, пока smoke не прошёл.

## 5. Этап C — доработка статьи по результатам серии

### C1. Методы (§5)

- Явно: N независимых пусков, одинаковый bag и offset; offset = отсечение взлёта; в контуре нет RNG.
- Протокольный срыв vs успешный ATE; failure rate.

- Сравнение только OpenVINS baseline vs adaptive.
- Ablation full = те же adaptive, что табл. 1.

### C2. Результаты (§6)

- Табл. 1: формат руководителя, **новые** mean±std / p / failure. Старые 0,493 / 1,806 / … не оставлять как основные.
- Негативный MH_04 D3 +40 % оставить, если подтвердится медианой; если нет — честно переписать вывод.
- Табл. 2: реальные median ATE по вариантам; не копировать adaptive табл. 1 в «full» вручную.
- §6.4: рисунки карты + измеренный r (или слабая связь). Фразу r = −0,72 не возвращать.
- c̄ дополнить p10 / долей skip, если средние снова «плоские».
- §6.2 натурка: одна фраза «не проводились; контур готов» — достаточно.

### C3. Гипотеза и выводы (§2, §7, аннотация, Abstract)

- Рабочие пороги 1,05 (clean) и 0,9 (degrade) по **медиане**.
- t-тест рядом, не вместо порогов.
- Новизна п. 5: диапазон применимости (в т.ч. умеренная засветка), не «мы сделали p-value».
- Ограничение: один стек (OpenVINS/MSCKF), EuRoC MH, синтетическая деградация D1/D3.
- Аннотация RU/EN должна совпадать с табл. 1 (не обещать «существенное повышение», если медиана это не держит).

### C4. Переносимость (вместо ORB-SLAM3 и чужих датасетов)

Формулировка, которую можно защищать:

> Экспериментальная проверка выполнена на открытой платформе OpenVINS (MSCKF) и последовательностях EuRoC MH_04/MH_05 при контролируемой деградации изображений. В этих рамках гипотеза о снижении ATE адаптивным масштабированием ковариации проверяется непосредственно (повторные пуски, сравнение с фиксированным шумом, ablation признаков). Численное сравнение с ORB-SLAM3, VINS-Mono и прогоны на KITTI/TUM-VI в работу не входили. Перенос на другие feature-based VIO с явным шумом измерений правдоподобен, поскольку меняется вес визуального обновления, а не детектор: тот же приём применим к EKF/MSCKF-оценщикам с ковариацией пиксельных невязок. Это остаётся перспективой, а не доказанным фактом.

Слова «исчерпывающе» не использовать. Сильнее: «протокол достаточен для проверки гипотезы на выбранной платформе».

### C5. Что из правок руководителя появится как тип результата
