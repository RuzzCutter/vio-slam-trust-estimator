## 0. Зафиксированные решения

| Вопрос | Решение |
|--------|---------|
| Где гонять | Только ваш локальный стенд. Старые RESULT_DIR там. При необходимости докачиваем EuRoC MH, не новые семейства датасетов. |
| Повторы | N **независимых пусков одного и того же bag**, одинаковые конфиг и деградация. Бюджет достаточный; лучше с запасом, часть пусков отпадёт. |
| `start_offset` | **Не менять между пусками.** Это отсечение взлёта (грязный участок), а не фактор рандомизации. Для каждой последовательности остаётся значение из `config/datasets.yaml` (MH_04 = 15 с, MH_05 = 5 с). |
| ORB-SLAM3, V1_03, KITTI, TUM-VI | В этом цикле **не запускаем**. В статье — обзор + формулировка переносимости гипотезы (см. §6). |
| Цифры из черновика руководителя | Формат таблиц (mean±std, p, failure, корреляция карты) берём. Конкретные значения v4/v5 **не** переносим. |

Почему offset не варьируем. Сдвиг старта меняет состав траектории и долю «грязного» взлёта. Тогда разброс ATE смешивает повторяемость фильтра и разный входной отрезок. Перед руководителем это не защитить: offset уже выбран как гигиена данных. Независимость пусков даёт ROS/init/тайминг при **том же** отрезке bag — это как раз то, что видно по старому расхождению 0,448 м vs 2,630 м на «одинаковом» adaptive.

## 2. Правила приёмки прогона (заранее, до серии)

Иначе «отбросить выброс» станет подгонкой.

### 2.1. Протокольный срыв (не входит в ATE)

Уже есть в стенде; оставляем и **обязательно** пишем в манифест:

- сбой инициализации OpenVINS;
- разрыв траектории > 0,5 с;
- расхождение: |координата| > 50 м;
- нет пары est/GT для `evo` (нет метрик).

Счётчики: `n_launch`, `n_fail`, `n_success`. В статье failure rate = n_fail / n_launch.

### 2.2. Успешный прогон

Есть TUM-траектория, `evo` посчитал ATE/RPE, нет флагов из §2.1.

### 2.3. Что не отбрасываем по ATE

Высокий ATE при формально успешной траектории (как 2,630 м) — **не** выброс для удаления из основной статистики. Это неустойчивость метода, её нужно видеть в std, медиане и min–max.

Дополнительно можно пометить run как `ate_high` (например ATE > Q3 + 1,5 IQR **внутри той же ячейки и того же режима**), но:

- в **основной** таблице остаются все `n_success`;
- trim-таблица — только в приложении / журнале, с явным правилом.

Так можно ответить руководителю: запас пусков нужен из‑за срывов init, а не чтобы выкинуть неудобные ATE.

### 2.4. Объём пусков

| Серия | Ячейки | Пусков на ячейку | Зачем |
|-------|--------|------------------|--------|
| Compare | все сценарии текущего `batch_paper.yaml` (10 условий × baseline+adaptive) | **9** независимых compare (каждый compare = 1 baseline + 1 adaptive) | Цель: ≥5 успешных **пар** на ячейку после срывов |
| Ablation | 4 сценария × {w/o f1..f4} | **7** adaptive на вариант | Full **не** гоняем отдельно: берём успешные adaptive из compare |
| Карта / корреляция | успешные adaptive MH_04 clean и MH_04 D1 σ=5 (минимум) | по всем успешным этих ячеек | Один r на черновик не рисуем: медиана r по пускам |

Если после 9 пусков успешных пар < 5 — догоняем эту ячейку ещё 3–5 пусками (`--resume`), не раздувая остальные.

Оценка порядка: ~10×9 compare + 4×4×7 ablation ≈ 90 compare-ячеек + 112 ablation-пусков. Compare-ячейка — два полных bag. Это много часов, но укладывается в заявленный бюджет; batch уже умеет `--resume`.

## 3. Этап A — доработка ПО (до серии на стенде)

Делать в этой ветке, проверять `dry-run` и одним коротким smoke (например MH_01 60 с × 2 пуска), полные MH — только у вас.

### A1. Повторы в batch

Файлы: `scripts/run_batch.py`, `config/batch_paper.yaml`, `config/batch_ablation.yaml`.

- В плане: `repeats: 9` (compare) / `repeats: 7` (ablation).
- Каждый повтор — новый `RESULT_DIR` (как сейчас: timestamp в имени). **Не** подмешивать seed в MSCKF.
- В `manifest.jsonl`: `repeat`, `seq`, `degrade`, `mode`/`ablate_variant`, пути, ATE, RPE, c̄, флаги срыва, `n_poses`.
- `start_offset` только из каталога или явного `advanced.start_offset`; для повторов не рандомизировать.
- Сохранить `--resume` (критично для длинной серии).

Идентичность bag: тот же путь к (деградированному) bag, тот же `openvins_config` / `euroc_mav_trust`, те же `trust_tau`, `c_skip`. Деградированные bag из кэша `datasets/euroc/degraded/` не пересобирать между повторами.

### A2. Сводка статистики для статьи

Файлы: `scripts/lib/run_results.py`, `scripts/build_tables.py`.

Для каждой ячейки (seq × condition × режим):

- n_launch, n_fail, n_success;
- median, mean, std (sample, ddof=1) ATE и RPE по успешным;
- min, max;
- mean c̄ по успешным adaptive;
- для compare: парный t-тест по **согласованным** повторам (повтор k: baseline_k vs adaptive_k), только если n_success пар ≥ 5; иначе p не публиковать, в таблице «—».

Выход: `paper_tables/table_repeats.md`, `.csv`, `.tex` — колонки как у руководителя (ATE base/adapt mean±std, ΔATE по **медианам**, p, c̄, Failure = n_fail/n_launch), но числа с серии.

ΔATE считать по медианам, не по одному старому прогону. В тексте можно дублировать mean.

Гипотеза на чистых: выполняется, если median(ATE_adapt) ≤ 1,05 · median(ATE_base).  
На деградации: median(ATE_adapt) < 0,9 · median(ATE_base).  
t-тест — дополнительный аргумент, не замена этих порогов (пороги уже в `эксперимент_v2.md`).

### A3. Общий adaptive-full для табл. 1 и 2

- Ablation-план **без** отдельных `full`.
- `build_tables.py --kind ablation` берёт full = успешные adaptive compare той же (seq, degrade).
- В markdown ablation: строка full совпадает с adaptive табл. 1 (те же n и median).

Это закрывает подмену full = 0,448 из другого смысла: 0,448 станет медианой новой серии или не станет — но источник будет один.

### A4. Поштучная ошибка и корреляция с доверием

Файлы: `scripts/evaluate_trajectory.py`, новый `scripts/correlate_trust_ate.py` (или расширение `build_trust_map.py`).

- При `--eval` сохранять поштучные ошибки после Sim(3): таблица `t, e_ate_m` рядом с `summary.txt` (через evo zip / повторный вызов с сохранением массива).
- Выровнять с `trust_log.csv` по времени (уже есть логика align в `build_trust_map.py`).
- Считать:
  - Pearson и Spearman: c(t) vs e(t);
  - то же для скользящего окна (окно по умолчанию 2 с или 20 отсчётов — зафиксировать в `meta.json`);
  - доля кадров c < c_skip;
  - квантили c: p10, p50, p90.
- По ячейке: медиана r по успешным пускам, размах, доля пусков с p < 0,05.
- Карты C(x,y) строить как сейчас (`build_trust_map.py`) для медианы-по-ATE пуска и для худшего успешного — две картинки в статью, не десять.

Если |r| окажется мал — в статью идёт факт, не цель «получить −0,72».

### A5. Журнал серии

Короткий апдейт `журнал_эксперимента.md` после каждого batch: id каталога, n_launch/n_fail, команды resume. Не дублировать все ATE в markdown вручную — источник истины `manifest.jsonl`.

Smoke на стенде до полной серии:

```text
python3 scripts/run_batch.py --plan config/batch_paper.yaml --dry-run
# затем 2 повтора MH_01 --duration 60 (или отдельный smoke-plan)
```

Критерий: два RESULT_DIR, два манифест-ряда, сводка n=2 без падения скрипта.

```text
python3 scripts/run_batch.py --plan config/batch_paper.yaml

python3 scripts/run_batch.py --resume datasets/results/batches/<id>
```

После серии:

```text
python3 scripts/build_tables.py --batch datasets/results/batches/<id> --out paper_tables/
```

Проверка ячеек: для каждой из 10 условий n_success пар ≥ 5. Иначе догон только дырявых ячеек.

Ожидаемые «трудные» ячейки (уже срывались): MH_05 D1 σ=5/9, MH_05 clean, MH_04 D1 σ=9. Их не исключать из плана заранее: failure rate — результат.

Тот же commit кода и те же degraded bag.


Сверка: median full в табл. 2 = median adaptive в табл. 1 для той же (seq, degrade).

### B4. Карта и корреляция

На успешных adaptive MH_04 clean и MH_04 D1 σ=5 (плюс по возможности MH_04 D3 +40 % — негативный сценарий):

В статью: 1–2 рисунка карты + одно предложение с median r (и что корреляция по пускам, не один прогон).

## 5. Этап C — доработка статьи

Файл: `Статья_v6.txt`. Цифры подставлять **только** из новых `paper_tables/` после B2–B4.

### C1. Методы (§5)

- Явно: N независимых пусков, одинаковый bag и offset; offset = отсечение взлёта.
- Протокольный срыв vs успешный ATE; failure rate.
- mean±std и медиана; парный t-тест при n_пар ≥ 5.
- Сравнение только OpenVINS baseline vs adaptive.
- Ablation full = те же adaptive, что табл. 1.

### C2. Результаты (§6)

- Табл. 1: новый формат руководителя, **новые** mean±std / p / failure. Старые одиночные 0,493 / 1,806 / … заменить или оставить в журнале как пилот, не как основные.
- Негативный MH_04 D3 +40 % оставить, если подтвердится медианой; если нет — честно переписать вывод.
- Табл. 2: реальные median ATE по вариантам; не копировать adaptive табл. 1 в одну строку «full» вручную.
- §6.4: качественная карта + измеренный r (или сообщение о слабой связи). Фразу про r = −0,72 не возвращать.
- c̄ дополнить p10/долей skip, если средние снова «плоские».

### C3. Гипотеза и выводы (§2, §7)

- Вернуть рабочие пороги 1,05 (clean) и 0,9 (degrade) по **медиане**.
- t-тест — рядом, не вместо порогов.
- Новизна п. 5: диапазон применимости (в т.ч. умеренная засветка), не «мы сделали p-value».
- Ограничение: один стек (OpenVINS/MSCKF), EuRoC MH, синтетическая деградация D1/D3.

### C4. Переносимость (вместо ORB-SLAM3 и чужих датасетов)

Нужная мысль руководителя: гипотеза не обязана быть проверена на всех SLAM сразу. Формулировка, которую можно защищать (не «исчерпывающе для всей робототехники»):

> Экспериментальная проверка выполнена на открытой платформе OpenVINS (MSCKF) и последовательностях EuRoC MH_04/MH_05 при контролируемой деградации изображений. В этих рамках гипотеза о снижении ATE адаптивным масштабированием ковариации проверяется непосредственно (повторные пуски, сравнение с фиксированным шумом, ablation признаков). Численное сравнение с ORB-SLAM3, VINS-Mono и прогоны на KITTI/TUM-VI в работу не входили. Перенос на другие feature-based VIO с явным шумом измерений правдоподобен, поскольку меняется вес визуального обновления, а не детектор: тот же приём применим к EKF/MSCKF-оценщикам с ковариацией пиксельных невязок. Это остаётся перспективой, а не доказанным фактом.

Слова «исчерпывающе» в тексте лучше не использовать: рецензент упрётся в один датасет и негативный D3 +40 %. Сильнее: «протокол достаточен для проверки гипотезы на выбранной платформе».

### C5. Что из правок руководителя в статье появляется как тип результата

| Идея правок | Как появится после плана |
|-------------|---------------------------|
| 5+ пусков, ±std, p | Табл. 1 с n_success, mean±std, p при n≥5 |
| Failure в таблице | Доля срывов, не бинарное «да/нет» с одного запуска |
| Согласованный ablation | Full = adaptive compare |
| Корреляция карты с ошибкой | Измеренный median r, не −0,72 |
| ORB-SLAM3 0,612 м | Не появится; абзац переносимости (§C4) |
| V1_03 доп. материалы | Не появится |
